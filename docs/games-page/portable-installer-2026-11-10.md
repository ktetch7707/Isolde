# Portable game installer and optical workflow boundary

The Games page supports deliberately narrow independent local-install formats: an inert ZIP bundle or POSIX USTAR archive, uncompressed or gzip-compressed, containing `isolde-game.json` with `schemaVersion`, `title`, `platform` and a relative `entrypoint`. Other tar compression formats and extended tar headers are unsupported. The entry point must be a Linux ELF file. Preflight inspects metadata and the ELF header without executing archive contents. Install requires a separate confirmation showing the selected installed file runtime and new profile-private destination.

It also accepts a standalone x86-64 Linux ELF executable, including from an approved optical disc. Preflight checks bounded ELF headers and an executable entry segment, rejects AppImages, and uses the filename as the title and PC as the platform. Confirmation shows that only the selected file is copied as `bin/game`; adjacent assets and libraries are not copied or resolved. This route is suitable only when the executable works without those files. Header inspection does not prove that the file is a game, safe, or compatible with the target runtime, and no content is run during inspection or installation. Its bytes are snapshotted, hash-checked against the review, and installed with the same managed recovery and uninstall protections as bundles.

The helper enforces a 512 MiB archive limit, 10,000-member limit and 2 GiB total expanded-size limit; rejects encrypted entries, duplicate/non-canonical paths, symlinks, unsupported special files and unsafe entry points; writes only into a new staging directory; and atomically publishes the completed package without replacing even a destination created during installation. Existing installations and saves are not overwritten or removed. Cancellation terminates the bounded helper and removes an uncommitted staging directory where possible. Failed catalog registration preserves the installed private folder for recovery rather than silently deleting it.

Play runs the registered native entry point in the selected file-runtime's isolated session, rather than passing it to that runtime as an emulator image. The selected runtime provides the session identity; it is not a compatibility layer or dependency installer. The package tree is mounted read-only in the game session; profile storage remains isolated. The title still runs as user-supplied executable code after the explicit install and Play actions, so the user must trust its source.

An explicit Uninstall action is offered only for a managed bundle installation that has no other catalog/edition references. The helper verifies the private install marker, exact directory/file inventory, file sizes and SHA-256 digests, then atomically moves the installation to `install.uninstall-pending` before the catalog entry is removed. If interrupted before catalog removal, reopening that profile restores the staged folder without overwriting an existing installation. After catalog removal, a second verification precedes cleanup. Cleanup removes only manifest-listed files after checking them again, and removes directories only when empty; unexpected files arriving during cleanup are not recursively deleted. Interrupted cleanup can leave an orphaned or partially cleaned pending folder; it is not automatically deleted on restart. Modified or unowned files cause a refusal; only the Isolde-managed install subtree is eligible, never its sibling profile/runtime/save folders. Checks cannot provide atomic protection against another process deliberately racing file replacement; keep external writers stopped during uninstall. A running or starting session blocks uninstall, and catalog source changes and game launch are blocked while it is in progress. Ordinary Remove from library remains catalog-only and preserves all files.

Games catalog tools offer explicit recovery of orphaned pending folders. Recovery checks the active profile and catalog references, refuses an occupied destination, and atomically restores remaining bytes without deleting anything or recreating a catalog record. Cleanup may already have removed part of the installation; inspect the restored folder before using it. Alternatively, the user can explicitly resume cleanup: the helper rechecks the remaining inventory and hashes, permits previously removed owned files, and refuses modified or unowned files. Saves outside the install remain untouched. If interruption removed the ownership marker, or the inventory is modified, cleanup cannot be resumed and the remaining folder must be inspected.

The same tools can find a complete private managed install left unregistered after a successful extraction but failed catalog write. The user selects an installed file runtime and confirms a candidate; a bounded helper verifies the private install marker, exact inventory, every file size and SHA-256, and the Linux ELF entry point before Isolde tries to add a fresh catalog record with original portable-install provenance. It never rewrites an existing entry, deletes files, or restores saves. Invalid/modified inventory, an occupied catalog identity, unavailable runtime, or failed catalog write leaves files untouched for retry or inspection. Marker validation is local integrity checking, not a signature, source authentication or proof of ownership. Discovery examines at most 10,000 profile install directories and lists at most 128 candidates.

The optical page observes mounted read-only ISO9660/UDF volumes and unmounted drives reporting media, without autorun. Unmounted data media can be explicitly mounted through UDisks with a read-only request; the returned mount is checked against the selected device and read-only state before use. The identity is SHA-256 over the entire block-device size reported by Linux, bounded to 16 GiB. Hashing occurs in the background, can take minutes and fails closed on short reads, unsupported block ioctls, missing device permission or a changed Linux disk sequence/size. Refresh retries a failed hash. The digest is cached only for the same device disk-sequence and size; it is not continuously rehashed and therefore does not detect in-place modification that fails to change the kernel disk sequence. It identifies bytes, not ownership or distinct bit-identical copies. ISO9660 volume-set/disc sequence metadata provides grouping; UDF is supported as a single-disc identity, without automatic set grouping. Old descriptor-only catalog entries and grants are preserved but do not match these new identities; explicitly register and approve the disc again.

An approved ISO9660 or UDF disc can register an executable relative path for direct Play. Only native Linux ELF files with executable mode bits are accepted; the exact media ID and profile grant are checked at catalog registration, Play resolution, session launch and sandbox preparation. The read-only disc tree is exposed only for the session. On a no-exec mount, ELF files, including shared libraries, are checked in sealed memory files and copied into a private temporary tree inside the isolated session; other regular files link back to the read-only disc. This preserves executable-relative `$ORIGIN` library paths without attempting executable mappings from the no-exec disc. Staging requires Linux memfd seals and an executable session temporary filesystem, and is limited to 512 MiB total ELF data, 32 path levels and 4,096 entries; special files and links outside the disc are refused. The disc is not remounted executable and no disc bytes are changed. A same-set ISO disc can be registered as another edition. If the expected disc is absent or another disc in the set is mounted, Play reports the expected number and requires the user to retry; no automatic launch or disc swap occurs. Eject is conservatively refused during any active or starting app session, or while an installer is using that drive. Otherwise it requests a normal UDisks unmount/eject and never forces a busy drive. Removing an optical catalog entry leaves the disc and all saves untouched.

The optical flow is not yet a full commercial disc-install lifecycle: no arbitrary vendor setup program, compatibility-runtime installer, DRM/activation bypass or in-game hot-swap continuation is claimed. If UDisks reports a busy mount, close the process using it and retry safe eject. An absent, unreadable or unsupported data volume reports a retryable mount error; audio-only media and drives that report no data sectors are not listed.

An active optical session publishes a typed pinned-media status, rechecking the profile grant, exact media, mount location and device observation. Removal, replacement, a different set disc, relocation and revoked approval produce a non-focus-stealing native-session notice directing the user to return Home and retry; Isolde never force-ejects or silently replaces that session's mount. Once interrupted, reinsertion cannot restore the pinned session even when the same content returns. The 2.5-second polling interval does not guarantee detection of every transient event, and platform-specific window managers may not display the notice. This is a recovery contract, not live swapping: the immutable sandbox bind mount cannot be retargeted after launch, and the notice does not observe or answer game-specific disc prompts. A real swap requires a separately reviewed, authenticated read-only media broker and an app/runtime protocol that can release and reopen media without granting the session host mount or device authority.

The device observation also includes the Linux mount-instance identifier, preferring the non-reused `statx` unique mount ID when available; this distinguishes a remount at the same path from the session's original bind mount. Older kernels' ordinary mount IDs can be reused, so they do not prove continuity. If mount IDs are unavailable, optical Direct Play is disabled rather than treating an untrackable mount as stable. Read-only inspection and safe eject remain available.

Not supported by this installer: arbitrary `.exe`/Windows installers, scripts, AppImages, self-extracting installer workflows, network installers, compatibility-runtime setup, dependency resolution, DRM/activation bypass, disk imaging, or automatic installer execution. A general third-party installer flow and original-disc install/play lifecycle remain T30.7/T30.8 coding gaps. No universal compatibility, gameplay, remote-only third-party setup, native build or physical-disc qualification is claimed here.

The catalog tools' Windows installer availability view probes only `/usr/bin/wine`, checks its resolved executable and root-owned non-writable ancestry, and never executes it. Missing, unsafe and unverified candidates all remain unsupported. A separately provisioned pinned, verified runtime plus a private-prefix, bounded installer/session adapter and explicit consent are required before advertising this route; system Wine presence alone does not establish support.

The same view offers an optional, read-only Windows PE preflight for a regular file up to 512 MiB in a profile-approved media folder. It checks bounded PE headers and reports architecture and full-file SHA-256 without executing or installing anything. It does not identify a vendor, validate signatures or ownership, prove safety, establish that a PE file is an installer, or enable compatibility installation.

Focused executable validation: `python3 tests/test_portable_game_installer.py`, plus the existing Games provisioning and Steam adapter tests. Native C++/QML integration still requires the repository's Qt/CMake test environment.
