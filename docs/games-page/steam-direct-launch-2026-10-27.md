# T30 direct Steam games — 2026-10-27

User authorization: implement selecting a Steam game in Isolde and pressing Play without manually navigating Steam. Steam may run in the background. This is the user-selected T30.5 slice; it grants no credit to unrelated Studio/Guide work or the complete Games gate.

## User workflow

1. Install Steam through Isolde's Store. First-time sign-in, game installation and any provider setup still belong to Steam.
2. In Games, choose **Add game → Steam**. Discovery reads installed titles in the active Isolde profile's managed Steam home. It makes no Web/API requests and reads no credential/account files.
3. Review the title/App-ID list. Cancel saves nothing; Import adds the reviewed games to the profile-local Games catalog. Repeated import preserves manual title corrections and Favorites.
4. Select a game card, open its details and choose **Play**. The trusted adapter rechecks its installed manifest, starts `/usr/games/steam -silent -applaunch <AppID>` inside the existing native sandbox, and waits for a process with that SteamAppId. Big Picture is not used as the per-game launch target.
5. Natural game exit or Home uses the existing SessionManager/ActionDispatcher return path. Missing/updating games, invalid identities and launch timeouts surface an error and retain the catalog entry for retry.

This implementation discovers fully installed games, not every title owned by an online Steam account. It does not claim entitlement from installation. Steam enforces sign-in, ownership, DRM, updates, Proton and third-party launcher requirements. Nonstandard game launchers that do not expose a SteamAppId-tagged process can time out rather than produce a false running-game claim. Existing Steam UI sessions must be returned from before starting another managed session.

At the original implementation checkpoint, external libraries were reported as unconnected and not granted filesystem access. The conservative connection slice below supersedes that limitation; no desktop-account or other-profile fallback is used.

## External Steam library connection — 2026-11-09

The Games toolbar now provides **Steam access** for the active profile. An explicit folder path can be approved only when it is a real Steam library under `/media` or `/mnt` with a local `steamapps` directory. Grants are stored separately per profile, bounded to eight non-nested libraries, and can be individually revoked. A disconnected previously approved mount remains listed but is not mounted until it is available again.

Steam discovery receives only that profile's approved library paths. Steam sessions mount each available approved root at its original path, read-only; the rest of the host mount tree remains unavailable. The adapter accepts manifests from the profile's managed Steam home or from the exact approved roots, rechecks App-ID/install identity before launch, and refuses unapproved external paths. The selected source remains read-only to avoid granting a game arbitrary write access to user-owned external storage. This may limit titles that require writing into their installation folder; such compatibility is not claimed. Revoking a grant does not delete files or catalog records. This is a conservative external-library connection slice, not evidence of real Steam-client/game acceptance.

## Lifecycle and save-return hardening — 2026-11-09

Direct Play now only observes App-ID-tagged processes carrying this launch's unique session token in the private PID namespace. It accepts either `SteamAppId` or `SteamGameId`, excludes known Steam client/service executables and still tolerates a three-second handoff gap. Bootstrap exit zero is not success; denial or timeout returns actionable account, ownership, connection, offline and installation guidance. Retry revalidates the manifest and starts a fresh session. The adapter does not read credentials or decide ownership: Steam remains the authority, including for cached offline entitlements.

On Home/cancel, the adapter signals only token-owned, tagged game processes first, waits up to five seconds for their exit, and gives the private client a three-second opportunity to handle exit/sync before signaling its token-owned processes. Natural game exit gets the same sync opportunity. The native host and desktop supervisor allow this bounded shutdown for direct Steam sessions; other apps retain their existing deadlines. A game that ignores termination is eventually stopped by namespace teardown. The grace period is **not** confirmation that local saves flushed or Steam Cloud synchronized; offline changes may need later Steam reconnect. Isolde does not delete or rewrite saves. The process marker means only a tagged process was observed, not authenticated ownership or playable gameplay. A tagged third-party launcher can precede the actual game, and launchers that remove the token or both identity variables cannot be tracked and may time out. Game crash status and cloud-sync completion cannot be inferred from this process interface.

Available checks: `tests/test_steam_games.py` passes 18/18 with inert manifests, simulated account denial/retry and launcher handoff, per-token identity and client exclusion, and a real isolated-token fixture that saves on termination while an unrelated process survives. `tests/test_games_provisioning.py` passes 14/14. Native Qt tests were extended for profile-private Steam saves and the delayed host shutdown, but were not built or run here. These fixtures do not establish Steam ownership, offline entitlement, genuine gameplay, game-specific save durability or cloud synchronization; installed-VM/real-title acceptance remains deferred.

Direct Steam sessions now remain in the starting state until the helper's exact, bounded, newline-delimited selected-App-ID process marker is received. A successful wrapper exit without that marker is an error. Cancellation before observation, failed sessions, and a profile change do not add a Continue Playing entry. Once a matching process has been observed, normal return can record activity; this is still a process observation, not proof of play or ownership. Steam-game errors are separate from Steam package failures: the error overlay directs the user back to the same game's Play action rather than offering to retry the Steam client or uninstall it. If the tagged game ignores termination, or the Steam supervisor cannot finish within its deadline, return reports that recent saves or Cloud sync may be incomplete. An orderly process exit and the bounded sync grace do not establish save or sync success.

Focused Qt regressions cover fragmented/overlong/wrong-identity markers, profile-scoped activity, cancellation, failure, focus restoration, synchronous startup failure and native-host shutdown errors; these tests are present but not run here because Qt/CMake are unavailable. Session teardown now waits for synchronous launch/exit calls to return before deleting the session, so reporting these failures does not destroy the currently executing object. Account-specific denial, reconnect, authentic Steam UI/client behavior and title-specific save/crash behavior still need controlled provider or installed-VM evidence.

## Implementation and boundaries

- The existing bounded `games`/edition tables store `runtime=steam`, an empty filesystem root and a validated positive uint32 Steam App ID in the provider target field. Existing catalog versions remain readable; no startup migration or rewrite is introduced. IDs, not commands/URIs/launch options, reach the dispatcher.
- `ComponentSchema` rejects arbitrary Steam paths, shell syntax, zero/leading-zero/overflow IDs and unknown registration fields. Direct `steam-game` layout actions are rejected. Only GameLibrary's current-profile identity resolver can supply the internal launch request; package definitions cannot contain `steamGameId`.
- Discovery is an asynchronous, cancelable helper with a 30-second deadline and 2-MiB response limit. The text-KeyValues reader bounds bytes/tokens/depth, rejects duplicate keys and nonregular metadata, uses descriptor-relative no-follow reads and excludes redirected/private-outside paths. Limits are 32 libraries, 5,000 titles and 10,000 entries; overflow refuses the import.
- The native adapter uses the Steam profile's existing private HOME/config/runtime, bus, PID and IPC boundaries. Steam and its games receive narrow gamepad-node grants. A per-profile native lock prevents duplicate managed Steam sessions.
- A zero-exit bootstrap is not gameplay or a running game. Startup waits up to 120 seconds for the requested tagged process; a three-second absence window tolerates launcher handoff. The adapter does not use global window names, host-wide process matching or `steam -shutdown` to close an existing client. Shutdown targets only a unique token inherited by this launch, using pidfds; namespace teardown remains the final owned-process boundary.
- Provider/game/save files are not edited by discovery or import. Actual Steam local-save flushing, Cloud synchronization, game/launcher/controller compatibility, offline first launch and crash behavior are not accepted from these code/tests. A supported commercial title still needs real runtime evidence.
